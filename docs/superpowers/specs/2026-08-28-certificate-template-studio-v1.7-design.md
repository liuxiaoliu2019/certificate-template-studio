# Certificate Template Studio v1.7.0 设计规格

- 状态：已由刘小刘批准
- 日期：2026-08-28
- 基线版本：v1.6.0
- 目标版本：v1.7.0
- 主题：质量闭环、标题设计、最少干预与上下文成本控制

## 1. 背景与结论

v1.6.0 已建立教材封面生成、现成模板双向转换、Style DNA、角色身份锁、三方案探索、横竖审批、修订回退、固定输出尺寸和公开发布验证。完整审计表明，它仍存在四类关键缺口：

1. 标题排版主要是单字体居中绘制，缺少语义分行、字体组合、字距、弧形、丝带和适应风格的设计系统。
2. manifest 的阶段字段不是严格状态机，部分动作能够越过分析、标题或审批前置条件。
3. 收尾报告、当前标题、Style Profile、审批原话和修订状态没有形成完整证据链。
4. references、prompts 和图片分析结果会在多轮任务中重复加载；多标题流程也没有真正可执行的快速通道。

v1.7.0 采用“质量托管模式”：保留严格质量门和用户最终审批，把风格选择、标题设计、候选筛选、一次自动修正、上下文路由和缓存命中交给 Skill 自动完成。默认对话极简，完整记录保存在项目中。

## 2. 目标

### 2.1 产品目标

- 用户以最少交互获得可批准、可恢复、可复用的横竖版证书 Master。
- 保留三方向探索，但默认只向用户展示自动评选的最佳横版。
- 显著提升中文、英文和中英混合标题的字体、层级与版式设计能力。
- 严格保持教材人物和动物角色的身份特征。
- 让现成横版或竖版模板稳定重制为横竖双 Master。
- 同教材或同模板的新标题默认复用已批准 Master，不重新探索主体风格。
- 通过缓存、阶段上下文包、差量修改和确定性脚本减少重复模型输入。

### 2.2 质量目标

- 不合格结果不得提交用户或批准为 Master。
- 标题、图片、Style Profile、布局计划、收尾报告和审批事件必须可追溯且彼此一致。
- 横版固定为 2172×1536 PNG，竖版固定为 1536×2172 PNG。
- 横竖标题整体外接框水平中心固定为画布 x=50%。
- 竖版标题相对 V3 基准上移约 110 px。
- 自动修正每个方向最多一次，不通过降低标准伪装成完成。

### 2.3 最少干预目标

正常新项目只在以下节点需要用户参与：

1. 模式未明确时选择模式。
2. 输入图片或标题缺失时补充内容。
3. 确认横版定稿或提出修改。
4. 确认竖版定稿或提出修改。

Style DNA、角色建档、风格推荐、标题模式、标题布局、候选评分、一次自动修正和竖版启动均默认自动执行。

## 3. 非目标

- 不在证书图片中生成姓名、正文、日期、学校、签名、印章等变量信息。
- 不承诺生成模型第一次输出必然完美；承诺不让未达标结果进入审批。
- 不把控制图合成到成品，也不复制其灰阶、纹理、轮廓或具体形状。
- 不把下载的教材封面、模板参考、标题参考或用户成品纳入公开仓库。
- 不在 v1.7.0 中建设完整图形编辑器、字体商城或在线项目管理平台。
- 不改变用户已经确认的目标输出像素。

## 4. 默认交互模式

### 4.1 智能启动菜单

当用户只说“使用 Skill 开始工作”时显示：

```text
请选择工作模式：
1｜教材封面生成证书
2｜现成模板双向转换

请回复 1 或 2。
```

如果同一条消息已经明确写出模式，则直接锁定模式，不重复显示菜单：

- “模式 1”“教材封面生成证书”等明确表达锁定 `textbook_cover`。
- “模式 2”“现成模板双向转换”等明确表达锁定 `template_bidirectional`。
- 图片类型或意图不明确时必须显示菜单，不允许推断。
- 同一条消息中的输入图片和标题同时接收，不再重复询问。

### 4.2 质量托管模式

教材模式仍完整规划并生成三套不同横版方向。系统完成身份检查、质量评分和一次自动修正后：

- 默认只展示综合得分最高的合格方案。
- 其他合格候选保存在项目中。
- 用户说“查看其他方案”时才展示其余候选和简洁差异。
- 默认不在对话中展开 Style DNA、七家族评分、Profile 参数或详细报告。
- 用户说“显示分析”“查看评分”或“查看报告”时按需展开。

默认横版提交文案保持简短：

```text
已完成横版候选生成与自动筛选，这是综合表现最佳的方案。

请直接提出修改，或回复“确认横版定稿”。
如需比较其他方案，请回复“查看其他方案”。
```

### 4.3 自动修正预算

- 首次生成三套横版后合并验收。
- 至少一套达到 85 分时直接提交最高分方案，不修正其他候选。
- 最高分为 75–84 分时，只修正最高分候选一次。
- 三套全部低于 75 分时，基于共同失败原因重新生成最有潜力的方向一次。
- 第二次仍低于 85 分时暂停并向用户报告主要阻塞。
- 竖版最多自动修正一次。
- 标题错字、多余文字、角色身份漂移等硬失败不参与普通分数平均，直接进入对应修正路由。

## 5. 总体架构

v1.7.0 将当前分散规则重组为九个边界清晰的组件。

### 5.1 Workflow Engine

负责唯一状态机、动作前置条件、恢复点和模式隔离。所有脚本更新 manifest 前后都必须通过状态转移和 Schema 校验。

### 5.2 Context Router

根据 `selected_mode`、当前阶段、活动候选和失败代码选择最小 reference、prompt、JSON 和图片集合。不得用“为保险起见”为每轮加载全部资料。

### 5.3 Project Cache

使用输入哈希和派生依赖关系判断 Style DNA、角色档案、标题布局、候选评估和 Master 是否仍有效。

### 5.4 Title Design Engine

先建立结构化标题布局计划，再按计划选择确定性程序渲染或经过验证的 AI 融合标题。它独立于底图生成，能够被横版、竖版和多标题流程复用。

### 5.5 Character Identity Engine

保存角色来源、裁切、不可改变特征和身份检查结果。任何实际使用角色的方案都必须通过身份硬门。

### 5.6 Quality Gate

由程序硬检查、一次性结构化视觉验收和用户审批三层组成。每一层只能把结果推进到下一层，不能代替下一层。

### 5.7 Revision Engine

负责 LEVEL1/2/3、锁定参数、旧证据失效、非破坏性历史和带哈希验证的回退。

### 5.8 Derivative Engine

负责同教材或同模板的多标题横竖双版本派生，不重新分析来源或探索主体风格。

### 5.9 Metrics

记录缓存命中、引用加载、模型调用、图片调用、自动修正和用户暂停次数，用于回归验证上下文成本。

## 6. 规范化状态机

### 6.1 通用原则

- manifest 中只保留一个当前阶段，不再混用多代同义阶段。
- 每个动作声明 `allowed_from`、`required_artifacts`、`invalidates` 和 `next_stage`。
- 任意失败不得部分写入正式状态；采用临时写入、验证、原子替换。
- 用户中断后以 manifest 和哈希为准恢复，不根据对话猜测阶段。
- 模式切换必须新建项目。

### 6.2 教材模式阶段

```text
initialized
→ analyzing_source
→ awaiting_title
→ planning_landscape
→ generating_landscape
→ validating_landscape
→ awaiting_landscape_approval
→ generating_portrait
→ validating_portrait
→ awaiting_portrait_approval
→ complete
```

辅助阶段：

- `revising_landscape`
- `revising_portrait`
- `deriving_title`
- `blocked`

主要前置条件：

- `planning_landscape` 必须已有有效 Style DNA、角色档案和非空用户标题。
- `generating_landscape` 必须已有三个合格且差异达标的 Style Profile 与标题布局计划。
- `awaiting_landscape_approval` 必须至少有一个通过质量门的横版候选和匹配的收尾报告。
- `generating_portrait` 必须已有明确批准的横版 Master。
- `complete` 必须有分别批准的横竖 Master。

### 6.3 模板模式阶段

```text
initialized
→ analyzing_source
→ awaiting_title
→ regenerating_source
→ validating_source
→ awaiting_source_approval
→ deriving_opposite
→ validating_opposite
→ awaiting_opposite_approval
→ complete
```

源方向可能是横版或竖版。另一方向在源方向批准前保持阻塞。

### 6.4 恢复行为

- “继续”读取当前状态并恢复下一项未完成动作。
- 已确认模式、标题和审批不重复询问。
- 哈希一致的 Style DNA、角色档案、Profile 和候选报告不重新计算。
- 哈希不一致时只使依赖该输入的下游产物失效。

## 7. 项目数据与缓存

### 7.1 新增结构化文件

每个文件都有独立 JSON Schema：

- `analysis/source_fingerprint.json`：来源图片、控制图和角色裁切哈希。
- `configs/active_context.json`：当前阶段最小工作快照。
- `title/<orientation>/title_layout_plan.json`：方向专属标题布局。
- `quality/<artifact>.quality_report.json`：统一质量报告。
- `configs/execution_metrics.json`：调用和缓存指标。
- `derivatives/<title-slug>/derivative_manifest.json`：多标题派生证据。
- `configs/migration_log.json`：旧项目迁移记录。

### 7.2 缓存失效规则

- 来源图片哈希变化：Style DNA、角色档案、全部候选和 Master 失效。
- 角色裁切或角色档案变化：所有使用该角色的候选和 Master 失效。
- 标题变化：只使标题布局、标题渲染和对应报告失效；主体 Master 保持可复用。
- Style Profile 变化：当前方向及其下游方向失效。
- 控制图变化：对应方向及其下游派生失效。
- 用户局部反馈：只使当前活动候选及其报告失效。
- 程序或 Schema 版本变化：按迁移规则判断是否需要重验，不默认重新生图。

### 7.3 active_context 限制

`active_context.json` 只包含：

- 模式和当前阶段；
- 当前标题；
- 活动候选与方向；
- 当前 Style Profile 和标题布局计划路径；
- 当前使用的角色 ID；
- 锁定参数；
- 最近失败代码；
- 下一允许动作。

不得复制完整 Style DNA、全部 revision 历史或完整 reference 文本。

## 8. 标题设计系统

### 8.1 混合渲染架构

标题处理顺序固定为：

1. 规范化用户原文，不改写内容。
2. 识别语言、词组和不可拆分语义单元。
3. 选择标题布局家族。
4. 生成方向专属 `title_layout_plan.json`。
5. 检查字体字符覆盖。
6. 生成无文字底图或 AI 融合标题。
7. 程序渲染或验证 AI 标题。
8. 执行标题专项评分和硬检查。

确定性程序标题用于文字准确性优先的扁平和效果标题；AI 融合模式只用于确实依赖插画化字形的设计，并必须提供视觉验收证据。

### 8.2 六类标题布局

1. `formal_two_tier`：正式双层，主行高权重，副行小字号宽字距。
2. `modern_two_tier`：现代双层，粗体主行与轻量副行形成对比。
3. `ceremonial_arc`：典礼弧形，主标题沿稳定弧线，副层保持可读。
4. `double_ribbon`：双层丝带，主标题和限定词分别进入主副丝带。
5. `playful_children`：儿童趣味字，允许逐字配色、轻微基线变化和圆润轮廓。
6. `illustrated_integrated`：插画融合标题，字形与主题装饰结合但文字必须准确。

### 8.3 标题容器规则

废除“所有横幅、丝带、卡片一律禁止”的全局规则，改为：

- 唯一主标题可以使用由标题计划明确声明的弧形、丝带或装饰底座。
- 该容器只能服务唯一主标题，不能承载姓名、正文、日期或伪文字。
- 容器必须与证书风格、边框语言和标题长度匹配。
- 非标题文字容器仍然禁止。
- `full_frame` 是证书四边结构，不等同于标题容器。

### 8.4 CERTIFICATE OF COMPLETION 硬规则

该标题禁止单行直排，只允许：

```text
CERTIFICATE
OF COMPLETION
```

或采用弧形、双层丝带表达。禁止拆成：

```text
CERTIFICATE OF
COMPLETION
```

双层直排时：

- `CERTIFICATE` 为主层。
- `OF COMPLETION` 高度为主层的 45%–60%。
- 副层使用更宽字距。
- 丝带形式中 `CERTIFICATE` 位于主丝带，`OF COMPLETION` 位于副丝带或副弧。

### 8.5 通用语义分行

- 英文优先在介词短语、限定词或语义边界处分行，不按字符中点机械切分。
- 中文优先保持固定词组、奖项名称和等级词完整。
- 中英混合标题分别建立语言层级，禁止把英文单词拆成字符。
- 最多两行；超过安全长度时优先更紧凑字体、字距和字号，再考虑同家族弧形或丝带布局。

### 8.6 字体策略

公开 Skill 内置少量可再分发的开源字体，覆盖四种角色：

- 正式中英衬线；
- 现代中英无衬线；
- 英文典礼展示字体；
- 儿童圆体。

字体优先级：

1. 用户为当前项目指定的字体文件或字体名称；
2. Skill 内置字体；
3. 明确记录的系统回退字体。

用户指定字体缺少标题字符时必须暂停说明，不允许静默替换。用户提供的商业字体只复制到当前项目，不进入公开仓库。

### 8.7 布局与评分

- 横版标题推荐宽度为画布的 52%–68%。
- 竖版标题推荐宽度为画布的 58%–72%。
- 标题整体外接框中心固定 x=50%。
- 竖版标题相对 V3 基准上移约 110 px。
- 横竖版可适配布局，但必须保持同一标题设计家族。

标题专项评分满分 100：

- 字体匹配 20；
- 层级 20；
- 设计感 20；
- 视觉平衡 15；
- 可读性 15；
- 横竖一致性 10。

低于 85 分不得提交。硬失败包括错字、缺字、错误语义分行、偏离水平中心、对比度不足、容器碰撞和扁平标题噪点。

自动修正顺序：字距与行距 → 字号比例 → 同角色兼容字体 → 语义双行 → 同家族弧形或丝带转直排。仍不合格则暂停。

## 9. 角色身份与来源证据

- 每个角色记录来源封面哈希、裁切路径、裁切哈希和边界框。
- 身份档案区分 `immutable_features` 与 `mutable_features`。
- 不可改变项包括发型或头部、脸部结构、肤色或毛羽色、服装分区、标志性配件、物种和身体比例。
- 可改变项包括姿势、动作、朝向、表情幅度和绘制媒介。
- 每个候选记录实际使用的角色 ID。
- 身份验收低于 85 分或任一不可改变项明显错误即硬失败。
- 角色过小、遮挡严重或裁切不足时暂停，请用户提供更清晰来源；不得猜测细节。
- 角色方案后续修改不得因 LEVEL3 或换风格自动解除身份锁。

## 10. 三层质量门

### 10.1 第一层：程序硬检查

不调用视觉模型，检查：

- 文件、路径和 Schema；
- 当前状态和动作前置条件；
- PNG、固定尺寸和比例；
- 标题与用户原文完全一致；
- 语义拆行规则；
- 字体字符覆盖；
- 标题中心和竖版位移；
- Style Profile、标题布局和渲染模式一致；
- 图片、报告和 manifest 哈希一致。

### 10.2 第二层：结构化视觉验收

首次三套横版合并为一轮验收，只输出固定字段和失败代码：

- 角色身份；
- 构图平衡；
- 左右视觉锚点；
- 边缘弱连接；
- 中央变量安全区；
- 标题设计；
- Style DNA 匹配；
- 多余文字或 Logo；
- 控制图痕迹。

报告示例：

```json
{
  "score": 89,
  "hard_failures": [],
  "repair_codes": ["TITLE_TRACKING_TIGHT"],
  "qualified": true
}
```

失败代码路由到最小修正 Prompt：

- `TITLE_TEXT_ERROR`
- `TITLE_LAYOUT_ERROR`
- `CHARACTER_IDENTITY_DRIFT`
- `LEFT_RIGHT_IMBALANCE`
- `SAFE_ZONE_INTRUSION`
- `STYLE_DNA_MISMATCH`
- `CONTROL_MAP_VISIBLE`
- `EXTRA_READABLE_TEXT`

### 10.3 第三层：用户审批

程序和视觉验收通过只代表可提交。只有用户明确肯定式批准当前对象才能成为 Master。

可接受：

- “确认横版定稿”
- “确认方案 1 为横版定稿”
- “确认竖版定稿”

必须拒绝：

- “不要确认横版定稿”
- “横版还不能定稿”
- “第一个可以”
- “不错”
- “继续”

审批事件必须绑定方向、当前标题、成品路径、成品哈希、收尾报告哈希、Style Profile、标题布局计划和用户原话。

## 11. 修订与回退

- LEVEL1 只允许局部视觉参数变化。
- LEVEL2 允许同风格家族内布局重组。
- LEVEL3 允许重新探索 Style Profile，但角色身份锁和唯一标题规则不可解除。
- 任何修订都使当前方向的旧收尾报告和旧批准状态失效。
- 横版修订还会使竖版 Master、竖版报告和竖版批准状态失效。
- 竖版修订不影响已批准横版。
- 历史审批事件保留为审计记录，但明确标记 `historical`，不能代表当前状态。
- 回退前必须验证目标文件存在且哈希与 revision 记录一致。
- 回退后重新生成收尾报告并重新审批，不复用旧审批。
- 所有修订文件采用新路径，禁止覆盖已有 revision。

## 12. 多标题快速通道

当横竖 Master 已批准且用户没有明确要求重新探索风格时：

1. 保存新标题。
2. 读取 Master Style Profile 和两个无文字底图或可安全清除的标题区。
3. 分别建立横版、竖版标题布局计划。
4. 允许在同一标题家族内选择兼容布局变体。
5. 重新渲染标题并执行程序硬检查。
6. 只在需要时执行标题区域视觉验收。
7. 写入独立 derivative manifest，不改变原 Master 标题和审批证据。

多标题流程不得重新：

- 分析封面或模板；
- 建立角色档案；
- 评分七个风格家族；
- 生成三套主体方案；
- 重构横竖主体画面。

只有用户明确说“重新探索风格”“重新设计主体”或来源文件发生变化时才退出快速通道。

## 13. Context Router 与成本控制

### 13.1 阶段上下文包

只定义七种上下文包：

- 封面或模板分析包；
- 风格与标题规划包；
- 横版生成包；
- 局部修改包；
- 竖版衍生包；
- 多标题派生包；
- 审批验证包。

每个包声明必需 reference、prompt、JSON、图片和最大文本体积。无关模式、安装文档、发布文档和完整历史不得进入模型上下文。

### 13.2 图片输入最小化

- 来源封面首次以足够细节分析一次。
- 后续角色生成输入完整封面低成本参考、实际使用角色裁切和身份摘要，不重复分析全部角色。
- 不使用角色的 `frame_led` 方案不加载角色裁切。
- 局部修改只加载当前成品和必要来源裁切。
- 模板模式只加载源模板、Template DNA、活动方向 Master 和目标控制图。

### 13.3 默认调用预算

全新教材项目正常路径：

- 封面完整视觉分析 1 次；
- 风格与标题规划 1 次；
- 横版生成 3 套；
- 横版合并视觉验收 1 轮；
- 横版自动修正最多 1 次；
- 竖版生成 1 套；
- 竖版视觉验收 1 轮；
- 竖版自动修正最多 1 次。

同教材新标题正常路径不重新分析来源、不重新探索三套、不重新生成主体。

### 13.4 Metrics

`execution_metrics.json` 至少记录：

- `cover_analysis_calls`
- `style_planning_calls`
- `image_generation_calls`
- `visual_review_calls`
- `automatic_repairs`
- `cache_hits`
- `cache_misses`
- `references_loaded`
- `prompt_characters_by_stage`
- `image_inputs_by_stage`
- `user_interruptions`

宿主提供真实 Token 数据时额外记录；不提供时使用调用次数、字符数和图片输入次数作为可比较代理指标。

## 14. 停止与错误处理

只有五类情况暂停用户：

1. 模式、输入图片或标题缺失。
2. 角色来源不足以可靠建立身份锁。
3. 每方向一次自动修正后仍无合格结果。
4. 等待横版或竖版明确审批。
5. 字体、图像生成能力、Schema、文件或环境验证失败。

错误处理要求：

- 错误信息说明当前阶段、失败代码、已保留产物和最小恢复动作。
- 不删除已有候选、修订或审批历史。
- 临时输出只有在图片和报告全部验证通过后才移动到正式路径。
- finalization 失败不得留下可被误认成正式 Master 的孤立文件。
- 当前环境没有生图能力时只生成分析、计划和 prompts，并明确标记 `blocked`，不得声称图片完成。

## 15. Schema 与脚本约束

- 所有运行时 JSON 在写入前后执行 Draft 2020-12 Schema 校验。
- 跨文件语义不变量由公共验证模块检查，不能只依赖 JSON Schema。
- 教材模式与模板模式复用同一审批、报告、状态转移、路径和哈希验证模块。
- Style Profile 注册不得覆盖同名文件；冲突时生成新版本 ID 或明确失败。
- finalization report 必须包含 `ratio_error_percent`，并与当前标题布局和字体证据绑定。
- `ai_integrated` 不再接受无证据的布尔参数；必须引用视觉验收报告和被验收图片哈希。
- 输出路径在指定 project root 时必须位于项目内部。
- 初始化使用临时目录，来源、控制图和初始 JSON 全部验证成功后再建立正式项目。

## 16. 兼容与迁移

- v1.6.0 项目保持可读，不直接重写历史文件。
- 提供显式迁移命令，把旧 manifest 转换到 v1.7.0 状态模型。
- 迁移前创建项目内备份并记录源版本、目标版本和文件哈希。
- 旧 Master 缺少完整报告时标记为 `legacy_unverified`，可查看但不能直接生成新的已批准派生版本。
- 用户可选择对旧 Master 重新收尾和验收，补齐证据后升级为有效 Master。
- 安装器继续采用不静默覆盖和时间戳备份策略。

## 17. 验证与验收标准

### 17.1 状态与审批测试

- 未分析来源不能进入规划或生成阶段。
- 未输入标题不能生成或批准。
- 仅空格标题必须拒绝。
- 否定式审批必须拒绝。
- 报告标题与 manifest 标题不一致必须拒绝。
- 报告模式与 Style Profile 标题模式不一致必须拒绝。
- 修改后旧报告和下游 Master 必须失效。
- 回退目标缺失或哈希变化必须拒绝。

### 17.2 标题测试

- `CERTIFICATE OF COMPLETION` 不得单行或错误拆行。
- 中文、英文和中英混合标题具备固定语义分行用例。
- 字体缺字必须停止，不能生成方框或静默替换。
- 横竖版标题中心误差不超过 1 px。
- 竖版标题位移记录为约 110 px。
- 六类标题布局均有至少一个确定性测试或结构化夹具。
- 扁平标题不得出现渐变、随机纹理或噪点。
- 相同输入和参数的程序标题输出哈希一致。

### 17.3 缓存与成本测试

- 相同来源不得重复分析。
- 标题变化只失效标题相关产物。
- 局部修改不得加载完整风格库或无关模式资料。
- 多标题不得重新探索三套。
- 每方向自动修正不得超过一次。
- 阶段上下文超过声明预算时验证失败。
- 记录的引用文件必须与 Context Router 的允许列表一致。

### 17.4 视觉和输出测试

- 横版严格为 2172×1536 PNG。
- 竖版严格为 1536×2172 PNG。
- 含角色候选必须绑定角色来源和身份报告。
- 左右角视觉锚点、边缘弱连接和功能安全区继续作为质量项。
- 控制图不得在成品中可见。
- 模板模式不得残留源文字、压扁边框或跳过源方向批准。

### 17.5 发布测试

- Windows、Linux，Python 3.10 和 3.12 继续通过。
- 公开仓库不包含用户图片、商业字体、本机路径、凭据或生成成品。
- 内置字体必须附带许可证、作者、来源、版本和哈希清单。
- 发布 ZIP 可复现，并包含运行所需字体、schemas、prompts、references 和 scripts。

## 18. 文档与用户可见变化

- README 默认使用示例改为智能启动方式。
- SKILL.md 从长篇规则入口调整为路由、状态和不可违反原则；细节保留在阶段 reference。
- 辅助命令示例必须包含新版收尾报告和审批所需参数，并在测试中真实执行。
- CHANGELOG 明确区分质量托管、标题引擎、状态机和迁移行为。
- 默认对话不展示内部评分；用户主动要求时可读取项目报告。

## 19. 设计完成定义

v1.7.0 只有同时满足以下条件才视为完成：

1. 两种模式都只能沿规范状态机推进。
2. 六种标题布局、语义分行、字体覆盖和精确定位可运行。
3. 标题容器规则不再与丝带需求冲突。
4. 审批证据链能拒绝否定话术、标题错配和旧报告。
5. 修订与多标题都有完整脚本、manifest 和测试闭环。
6. 缓存、阶段上下文包和 Metrics 能证明没有无故重复分析。
7. 正常新项目达到约定的最少交互路径。
8. 现有快速验证、公开发布验证和新增边界测试全部通过。
9. 公开安装包不包含用户内容或不可再分发字体。
10. README、SKILL.md、schemas、示例和脚本行为一致。
